# 验收卡：lightweight-project-truth

## 目标

为 OpenATDD 增加精简的项目事实层，让后续开发自动获得当前产品规则、架构边界和关键技术决策，同时保持低 Token、避免重型文档流程

## 建议用户旅程

1. 项目首次运行 `openatdd init`，获得一份可直接填写、不会覆盖已有内容的精简项目事实文件。
2. 技术负责人只记录当前仍有效的产品规则、架构边界和关键技术决策，不维护 Vision / Epic 等重型流程文档。
3. 以后创建或恢复开发任务时，OpenATDD 自动把该文件作为有来源摘要的实现与验证上下文；项目事实改变后，旧上下文自动失效并重建。
4. Agent 按当前项目事实完成开发和验证，原有 incident、不变量、历史验收与路径影响分析继续生效。

## 验收标准

### AC-01 [AUTO] [BLOCKING] 初始化产生单一、精简且可安全维护的项目事实源
- 前提：一个新项目或已有 `.openatdd/` 的旧项目。
- 操作：执行 `openatdd init`。
- 结果：存在一份带有产品规则、架构边界、关键技术决策三个明确区域的项目事实模板；重复初始化不覆盖人工内容，也不新增审批或文档层级。
- 证据：初始化与重复初始化的确定性测试，以及生成文件断言。

### AC-02 [AUTO] [BLOCKING] 后续任务自动获得当前项目事实
- 前提：项目事实文件中已经填写可识别的当前规则。
- 操作：创建并评估新任务，或构建该任务的作用域上下文。
- 结果：任务的实现与验证上下文都包含一个来源可追溯的 `ProjectTruth` 引用，无需人工再查询；CLI 只返回精简元数据，不复制整份正文到任务状态或输出。
- 证据：任务创建、知识检索和 `context-build` 集成测试。

### AC-03 [AUTO] [BLOCKING] 项目事实变更会使派生认知自动更新
- 前提：任务上下文和知识图谱已经从项目事实构建完成。
- 操作：修改项目事实文件中的一条当前规则并再次加载上下文或图谱。
- 结果：来源摘要发生变化，旧上下文被判定为 stale，重建后只能看到新的当前事实；项目事实仍是唯一事实源，图谱只是可重建索引。
- 证据：图谱 stale、上下文 stale 与重建测试。

### AC-04 [AUTO] [BLOCKING] 保持兼容、低开销和原有长期记忆能力
- 前提：旧项目没有项目事实文件，或项目已有 incident、invariant、standard、research 数据。
- 操作：升级后执行现有工作流和完整测试。
- 结果：旧项目可自动补齐模板且继续运行；原有记忆、历史影响与检索不退化；不引入模型调用、外部服务、数据库、Vision/Epic/Issue 层级或新的人工确认。
- 证据：现有知识/工作流回归测试与项目完整检查。

## 边界

- 项目事实只保存“当前仍有效”的事实；变更历史继续由任务、decision、incident 和 Git 承担。
- 本次提供初始化、索引、自动注入和失效重建能力，不尝试由 AI 自动猜测或持续改写项目事实。
- 文件保持短小、普通文本、可审查；不新增独立命令和第三张人工验收卡。
