# 验收卡：acceptance-outcome-routing

## 目标

根据验收表面将完成结果路由为自动接受、人工复核或人工 UAT，避免所有需求统一要求人工 UAT

## 建议用户旅程

1. 开发者为需求写出带 `AUTO`、`ASSISTED`、`MANUAL` 分类的验收标准，并完成实现与自动验证。
2. OpenATDD 根据验收标准确定最终报告只需提供自动证据，还是还需附带人工 UAT 步骤。
3. AI 交付后任务默认结束；人没有异议无需再次确认，只有发现问题时才反馈并重开修复。

## 验收标准

### AC-01 [AUTO] [BLOCKING] 确定性技术改动验证后直接交付
- 前提：任务的阻塞验收标准均可由命令或测试确定性验证，且没有要求人工判断的验收表面。
- 操作：完成正式 finalization。
- 结果：系统进入 `DELIVERED`，报告明确列出已通过证据，不要求人重复执行测试，也不增加第三次批准。
- 证据：状态机与报告渲染测试覆盖纯内部接口、重构或同类全自动验收任务。

### AC-02 [AUTO] [BLOCKING] 接口与业务契约提供结果供人按需检查
- 前提：任务包含内部或对外 API、业务契约或 `ASSISTED` 验收表面，AI 已执行可自动完成的验证。
- 操作：负责人打开验收报告查看请求、响应、状态码、权限、异常和副作用等结果。
- 结果：负责人不必为了形式重新调用接口，也不必回复“批准”；没有异议即维持 `DELIVERED`，有异议则反馈具体问题。
- 证据：API/辅助验收 fixture 的状态、报告、通知与无额外批准断言。

### AC-03 [AUTO] [BLOCKING] 只有真正需要人执行的场景附带人工 UAT
- 前提：任务存在阻塞的 `MANUAL` 验收标准，例如主观视觉、真实设备、生产权限或无法自动观察的第三方行为。
- 操作：完成正式 finalization。
- 结果：系统仍进入 `DELIVERED`，但报告清楚区分 AI 已验证部分和建议人执行的 UAT 步骤；人执行后没有问题无需回复，发现问题才提出异议。
- 证据：阻塞与非阻塞 `MANUAL` 组合的报告路由测试。

### AC-04 [AUTO] [BLOCKING] 人的异议会重开同一个任务
- 前提：任务已经 `DELIVERED`，用户查看结果或执行人工 UAT 时发现与需求验收卡不符。
- 操作：用户描述具体异议，无需填写新卡。
- 结果：系统进入修复流程，记录缺陷、重新验证完整旅程并再次交付；没有异议时不产生额外状态转换。
- 证据：已交付任务的缺陷重开、修复和重新 finalization 测试。

### AC-05 [AUTO] [BLOCKING] 现有任务与命令保持兼容
- 前提：项目已有 `AUTO`、`ASSISTED`、`MANUAL` 契约、历史任务和 finalization manifest。
- 操作：升级后继续使用现有 CLI 创建、恢复、验证和 finalize 任务。
- 结果：旧 `READY_FOR_UAT` 数据可读取；现有验证语义不削弱；CLI 输出、README、Skill 指令和测试与异议驱动的交付闭环一致。
- 证据：完整项目测试、旧状态 fixture 回归测试和 npm 打包检查。

## 边界

- 本次改变的是完成后的验收收口，不改变 Quick、Standard、Deep 复杂度路由及风险 overlay。
- `DELIVERED` 表示 AI 已完成约定工作并提交结果，不伪称人做过显式签收；所有阻塞自动标准仍必须有当前 verification epoch 的正式证据。
- 不自动部署、不替人批准发布，也不把对外 API 一律判为人工 UAT。
- 人工 UAT 是交付报告中的验证方式，不新增第三张卡或第三个批准门；旧任务状态必须继续可恢复。
